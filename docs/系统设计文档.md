## 1. 目标与角色

管理一个班级的班费账目，做到 **公开、透明、可追溯、好对账**。

| 角色（界面中文名） | 标识 | 权限 |
|------|------|------|
| 生活委员 | `ADMIN` | 收支录入与作废、**小票上传**、成员账号管理、收费批次、发布公告、全部查询 |
| 普通成员 | `MEMBER` | 查看收支明细（含小票）、查看本人缴费状态、查看公告 |
| 班长 | `MONITOR` | 同 `ADMIN`（第十四轮新增，用于承载「班长」这一班级职务） |
| 班主任 | `TEACHER` | **运营全权（第七轮起与 ADMIN 同权）**：收支录入/作废/删除、**小票上传**、成员账号管理（建号/编辑/重置密码/停用）、收费批次、公告与全部查询 |

> **三个运营角色同权**：`ADMIN`(生活委员) / `MONITOR`(班长) / `TEACHER`(班主任) 都在 `STAFF_ROLES` 内，权限完全一致（第七轮起 TEACHER 已与 ADMIN 同权，第十四轮新增 MONITOR 不引入新权限档，只为让「班长」这一称谓有独立标识）。`MEMBER`(普通成员) 只读。**接口契约与 Java 版一致**：`MEMBER/ADMIN/TEACHER` 未改名，仅新增 `MONITOR`；界面中文名只存在于 `types/index.ts` 的 `ROLE_TEXT`。班级信息里的「班主任」是 `cls_class.head_teacher` **独立字段**（班主任姓名），与角色无关。

**权限实现**：路由守卫（前端隐藏入口）+ 后端角色路由表 `_STAFF_ROUTES`（中间件强制校验，表内路径仅 `STAFF_ROLES={ADMIN,MONITOR,TEACHER}` 可访问，其余 `/api` 路径=任意登录角色），前端隐藏不算安全边界。

**核心业务规则**
1. 流水表**默认只增不改**：记错了优先用「作废」（红冲），原记录保留 → 账目可追溯；管理员可**物理删除**（条件删除防并发双扣：NORMAL 同事务回滚余额并联动批次缴费状态退回 UNPAID，VOID 直接清除），列表默认隐藏已作废（需查时用状态筛选）。
2. 余额 = `SUM(收入 NORMAL) − SUM(支出 NORMAL)`，落库时在同一事务内同步冗余到 `cls_class.balance`，定期用流水对账。
3. 金额一律 `DECIMAL(10,2)`，**禁止 float/double**。
4. 成员缴费与流水的同事务写入（`fee_record` + `fee_payment.status` + 余额）在**收费批次「标记缴费」**（`POST /batches/{id}/pay`）路径实现；收入登记页不直接关联缴费，避免出现第二条资金写入路径（见 §5 已知限制）。
5. **缴费对象 = 除班主任外的全部学生**（第二十轮口径）：建批次（`POST /batches`）与缴费名单（`GET /members`）都取 `role IN (MEMBER, ADMIN, MONITOR)` 的启用账号，**只有班主任 `TEACHER` 排除**。依据是 `batch_service.PAYABLE_ROLES` 这一个常量，两处必须同口径。

   口径演进：Java 原版是「所有启用账号都算」（含班长）→ 第十四轮改成「只算 `MEMBER`」，理由是「运营角色是管账的人不该进名单」→ **第二十轮改回「除班主任外全员」**。第十四轮的理由只对班主任成立：班主任是 `.env` 声明的老师账号、不是学生；而生活委员与班长是在班里承担班务的**学生**，班费照交。旧口径的真实后果是**班里收不到他们的班费**（不在名单 → 缴费页列不出 → 无处登记）。班主任因此没有「我的缴费」入口（`router` / `SideNav` 的 `roles` 已排除 `TEACHER`），见 §8 交付记录。

## 3. 技术架构

```
浏览器
  └─ Vue3 (Vite)  ── axios + JWT ──┐
      ├─ Vue Router 4  路由守卫      │  /api/**
      ├─ Pinia        登录态        ▼
      ├─ Element Plus  UI        FastAPI (Python 3.13)
      └─ ECharts 5    图表        ├─ auth 依赖            登录校验
                                 ├─ _STAFF_ROUTES 中间件 角色校验（22 条路由）
                                 ├─ require_role         端点级角色兜底
                                 ├─ 异常处理器           统一错误响应
                                 ├─ Service (会话/事务) ── SQLAlchemy 2.0
                                 └─ R<T> 统一响应          │
                                                          ▼
                                                    MySQL 8 (utf8mb4)
```

**选型理由**
- **JWT 而非 Session**：前后端分离、免状态、便于以后小程序接入；代价是无法主动踢人 → 用短有效期 + 刷新解决。
- **FastAPI + SQLAlchemy 2.0**：Pydantic 模型同时是校验层与 OpenAPI 文档来源；同步会话事务直白，单表 CRUD 走 ORM、复杂筛选落原生 SQL，轻量可读。
- **单一流水表**（收入支出同表）：余额与统计只需一次 `SUM/CASE WHEN`，不用两张表再 union。
- **冗余余额列**：仪表盘高频读，避免每次聚合；用事务保证与流水一致。

## 4. 数据库设计（MySQL 8 / utf8mb4 / InnoDB）

```sql
-- 1) 班级
CREATE TABLE cls_class (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  class_name  VARCHAR(50)  NOT NULL                COMMENT '班级名称，如 计科2201',
  grade       VARCHAR(20)  NULL                    COMMENT '年级/届别',
  head_teacher VARCHAR(50) NULL                    COMMENT '班主任',
  balance     DECIMAL(12,2) NOT NULL DEFAULT 0.00  COMMENT '冗余余额，由流水对账',
  status      TINYINT      NOT NULL DEFAULT 1      COMMENT '1启用 0停用',
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id)
) ENGINE=InnoDB COMMENT='班级';

-- 2) 用户
CREATE TABLE sys_user (
  id           BIGINT      NOT NULL AUTO_INCREMENT,
  class_id     BIGINT      NOT NULL,
  username     VARCHAR(32) NOT NULL                COMMENT '登录名=学号',
  password     VARCHAR(100) NOT NULL               COMMENT 'BCrypt 密文',
  real_name    VARCHAR(32) NOT NULL,
  student_no   VARCHAR(20) NULL,
  role         ENUM('ADMIN','MEMBER','TEACHER') NOT NULL DEFAULT 'MEMBER',
  phone        VARCHAR(20) NULL,
  status       TINYINT     NOT NULL DEFAULT 1,
  last_login_at DATETIME   NULL,
  created_at   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_username (username),
  KEY idx_class (class_id)
) ENGINE=InnoDB COMMENT='系统用户/班级成员';

-- 3) 收支类别
CREATE TABLE fee_category (
  id       BIGINT  NOT NULL AUTO_INCREMENT,
  class_id BIGINT  NOT NULL,
  name     VARCHAR(30) NOT NULL COMMENT '如 班费收取/活动物资/饮水/打印',
  kind     ENUM('INCOME','EXPENSE') NOT NULL,
  icon     VARCHAR(50) NULL COMMENT 'Element Plus 图标名',
  sort     INT NOT NULL DEFAULT 0,
  status   TINYINT NOT NULL DEFAULT 1,
  PRIMARY KEY (id),
  KEY idx_class_kind (class_id, kind)
) ENGINE=InnoDB COMMENT='收支类别字典';

-- 4) 收支流水（核心表，记错优先作废，管理员可物理删除）
CREATE TABLE fee_record (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  class_id    BIGINT       NOT NULL,
  type        ENUM('INCOME','EXPENSE') NOT NULL,
  category_id BIGINT       NOT NULL,
  amount      DECIMAL(10,2) NOT NULL              COMMENT '恒为正数，方向由 type 决定',
  title       VARCHAR(60)  NOT NULL                COMMENT '摘要，如 收取XX班费/购买班级活动矿泉水',
  occurred_at DATETIME     NOT NULL                COMMENT '业务发生时间（非录入时间）',
  channel     ENUM('CASH','WECHAT','ALIPAY','BANK','OTHER') NOT NULL DEFAULT 'CASH',
  payer_user_id BIGINT     NULL                    COMMENT '收入：缴费人；支出：收款方留空',
  batch_id    BIGINT       NULL                    COMMENT '来自收费批次',
  remark      VARCHAR(255) NULL,
  receipt_url VARCHAR(255) NULL                    COMMENT '票据图片路径',
  status      ENUM('NORMAL','VOID') NOT NULL DEFAULT 'NORMAL' COMMENT '作废=红冲',
  created_by  BIGINT       NOT NULL,
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  voided_by   BIGINT       NULL                    COMMENT '作废人（第十九轮审计）',
  voided_at   DATETIME     NULL                    COMMENT '作废时间',
  PRIMARY KEY (id),
  KEY idx_class_time (class_id, occurred_at),
  KEY idx_type (class_id, type, status),
  KEY idx_payer (payer_user_id)
) ENGINE=InnoDB COMMENT='班费收支流水';

-- 5) 收费批次 + 每人缴费状态
CREATE TABLE fee_batch (
  id         BIGINT       NOT NULL AUTO_INCREMENT,
  class_id   BIGINT       NOT NULL,
  name       VARCHAR(60)  NOT NULL                COMMENT '如 2026春季班费',
  amount     DECIMAL(10,2) NOT NULL               COMMENT '每人应收',
  deadline   DATE         NULL,
  remark     VARCHAR(255) NULL,
  status     ENUM('OPEN','CLOSED') NOT NULL DEFAULT 'OPEN',
  created_by BIGINT       NOT NULL,
  created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  closed_by  BIGINT       NULL                    COMMENT '关闭人（第十九轮审计）',
  closed_at  DATETIME     NULL                    COMMENT '关闭时间',
  PRIMARY KEY (id),
  KEY idx_class (class_id)
) ENGINE=InnoDB COMMENT='收费批次';

CREATE TABLE fee_payment (
  id         BIGINT       NOT NULL AUTO_INCREMENT,
  batch_id   BIGINT       NOT NULL,
  user_id    BIGINT       NOT NULL,
  amount     DECIMAL(10,2) NOT NULL DEFAULT 0.00  COMMENT '实收，可大于应收',
  status     ENUM('UNPAID','PAID','REFUNDED') NOT NULL DEFAULT 'UNPAID',
  channel    ENUM('CASH','WECHAT','ALIPAY','BANK','OTHER') NULL,
  paid_at    DATETIME     NULL,
  record_id  BIGINT       NULL                    COMMENT '关联 fee_record.id',
  remark     VARCHAR(255) NULL,
  created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_batch_user (batch_id, user_id),
  KEY idx_user (user_id)
) ENGINE=InnoDB COMMENT='成员缴费状态';

-- 6) 公告
CREATE TABLE sys_notice (
  id           BIGINT      NOT NULL AUTO_INCREMENT,
  class_id     BIGINT      NOT NULL,
  title        VARCHAR(80) NOT NULL,
  content      TEXT        NOT NULL,
  pinned       TINYINT     NOT NULL DEFAULT 0,
  status       TINYINT     NOT NULL DEFAULT 1      COMMENT '1发布 0草稿/下架',
  published_at DATETIME    NULL,
  created_by   BIGINT      NOT NULL,
  created_at   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by   BIGINT      NULL          COMMENT '最后编辑人（第十九轮审计）',
  updated_at   DATETIME    NULL          COMMENT '最后编辑时间',
  PRIMARY KEY (id),
  KEY idx_class (class_id, pinned DESC, published_at DESC)
) ENGINE=InnoDB COMMENT='班级公告';
```

> **审计留痕的边界（第十九轮）**：上面三张表的审计列只覆盖**作废 / 关闭 / 编辑**三类动作。`DELETE /records/{id}`、`DELETE /batches/{id}`、`DELETE /notices/{id}` 是**硬删**，行不存在了自然留不下痕迹 —— 这是物理事实，不是遗漏。留痕路径是「**作废 / 下架**」，界面文案一律引导「记错优先作废」。公告删之前必须先下架，而下架本身就是一次 `update`，所以「谁下的架」被 `updated_by` 记下了，「谁删的行」仍查不到。

**关键查询（仪表盘）**

```sql
-- 本月收入 / 支出 / 余额（一次扫表搞定）
SELECT
  SUM(CASE WHEN type='INCOME'  AND status='NORMAL' THEN amount ELSE 0 END) AS income,
  SUM(CASE WHEN type='EXPENSE' AND status='NORMAL' THEN amount ELSE 0 END) AS expense
FROM fee_record
WHERE class_id = ? AND occurred_at >= '2026-09-01' AND occurred_at < '2026-10-01';

-- 近 6 月趋势
SELECT DATE_FORMAT(occurred_at,'%Y-%m') AS ym,
       SUM(CASE WHEN type='INCOME'  THEN amount ELSE 0 END) AS income,
       SUM(CASE WHEN type='EXPENSE' THEN amount ELSE 0 END) AS expense
FROM fee_record WHERE class_id=? AND status='NORMAL'
  AND occurred_at >= DATE_SUB(CURDATE(), INTERVAL 6 MONTH)
GROUP BY ym ORDER BY ym;

-- 缴费完成率
SELECT COUNT(*) AS total, SUM(status='PAID') AS paid FROM fee_payment WHERE batch_id=?;
```

**初始数据**：预置 `cls_class` 一行、`ADMIN` 账号（BCrypt 初始密码，强制首登改密）、
收入类别 `班费收取/义卖收入/捐款/退款/其他`，支出类别 `活动物资/打印资料/饮用水/班会布置/交通/其他`。

## 5. 接口设计（REST，统一前缀 `/api`）

**统一响应**：`{ "code": 200, "message": "ok", "data": { ... } }`
`code`：`200` 成功 ｜ `401` 未登录/过期 ｜ `403` 无权限 ｜ `400` 参数错误 ｜ `1xxx` 业务错误 ｜ `500` 系统异常。

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| POST | `/auth/login` | 登录，返回 `{token, user}` | 公开 |
| GET | `/auth/me` | 当前用户信息 | 登录 |
| PUT | `/auth/password` | 修改密码（校验旧密码） | 登录 |
| GET | `/auth/profile` | **第十五轮**：读本人完整资料（`account_vo`，含学号/手机号/状态/时间戳）。只认登录令牌里的 id，**只能读自己** | 登录（**含普通成员**） |
| PUT | `/auth/profile` | **第十五轮**：本人自助改 `realName`/`studentNo`/`phone`（三者皆可选，语义同运营编辑：不传=不改、空串=清空、学号同班唯一）。**请求体不接受 id**，改谁由令牌决定；`role`/`status`/`username`/`classId` 传了也无效 | 登录（**含普通成员**） |
| GET | `/dashboard/summary` | 余额/本月收支/缴费率/最新5笔/置顶公告 | 登录 |
| GET | `/dashboard/trend?months=6` | 月度收支趋势 | 登录 |
| GET | `/dashboard/category-pie?months=6` | 支出分类占比 | 登录 |
| GET | `/records` | 流水分页，`page,size,type,categoryId,keyword,status,id,start,end`（`id` 精确跳转，与其余条件 AND） | 登录 |
| POST | `/records` | 新增收支；`receiptUrl` 可选（**仅 EXPENSE**，须为 `/api/files` 返回的已存在路径） | 运营（ADMIN/TEACHER） |

**全局约定**
- 鉴权依赖：无 `token` → 401；`_STAFF_ROUTES` 表内路径（记账与账本导出/类别/成员/账号增删改/批次/小票上传/公告写/班级信息写共 **22** 条）先于 body/query 校验校验角色，`role not in STAFF_ROLES={ADMIN,MONITOR,TEACHER}` → 403「当前角色无权执行该操作」；端点级依赖用 `require_roles(...)`。停用账号（`status=0`）登录 → 403「账号已被停用，请联系班长」，密码错 → 401。
- 账号管理语义：用户名全局唯一（不分班级，重名 400）；**学号 `studentNo` 可与登录名不同、同班唯一**（DDL 未建唯一索引，服务层校验，重号 400「该学号已存在」；编辑语义同 phone：**空串=清空、不传=None=不改**）；`class_id` 取操作者所在班级；**停用**（`status=0`）保历史、仅禁登录；**删除**（第十二轮）只放行「零引用」账号——四类引用（记账人/缴费人、缴费行、批次创建者、公告发布者）任一命中即 400 并引导改用停用，保证账目不出现悬空引用；本人改密走 `PUT /auth/password`（需旧密码），运营重置他人密码走 `PUT /users/{id}`。
- 环境变量（`config.py`）：数据库用 `CLASSFEE_DB_URL/USERNAME/PASSWORD`（旧 Java 版的 `SPRING_DATASOURCE_*` 仍兼容但不推荐）；`CLASSFEE_JWT_SECRET` 是**当前 Python 后端**签发/校验登录令牌用的密钥（非 Java 遗留，改动会让已登录会话全部失效）；`CLASSFEE_TEACHER_*` 声明班主任账号；`CLASSFEE_UPLOAD_DIR` 小票目录。仓库根目录提供 `.env.example` 模板与 `.env`（compose 自动读取，已加入 `.gitignore`）。
- 账号来源：**无注册页，只有登录页**。① 运营账号（默认**班长** `TEACHER`）在部署配置里声明（`CLASSFEE_TEACHER_USERNAME` / `CLASSFEE_TEACHER_PASSWORD`，可选 `NAME` / `ROLE=ADMIN|TEACHER`），启动时**仅在不存在时创建、已存在则跳过且不覆盖**（本人自助改密不会被改回）；用户名与密码必须同时填写，代码里无默认口令。② 其余成员账号由运营角色登录后经 `/api/users` 创建并授权（角色三选一：普通成员 / 生活委员 / 班长）。
- 小票语义（第八轮）：`receiptUrl` 只接受上传接口返回的相对路径（正则 `receipts/<name>`，空白串归一为「未挂」）；**仅 EXPENSE 可挂**（INCOME 传入 400「仅支出流水可上传小票图片」）；文件不存在 400「小票文件不存在或已失效，请重新上传」；上传后未挂账前该路径不可读（404，只有本班流水引用才放行）；`DELETE /records/{id}` 提交成功后回收磁盘文件（仍被其他流水引用则保留，回收失败不阻断删除）。
- 公告与班级信息语义（第十轮）：两者**读全员、写运营**（`GET` 不进 `_STAFF_ROUTES`，写接口进）。公告「下架」= 软删除（`status=0`，成员不可见、运营可恢复并补发布时间），「彻底删除」要求先下架（否则 400，避免误删无从找回）；`GET /notices?status=0|all` 对非运营角色静默降级为「已发布」，不泄露下架内容。仪表盘 `pinnedNotices` 只取**已发布且置顶**的最近 3 条（对齐 Java `SummaryVO.pinnedNotices`）。班级信息只开放名称/年级/班主任三项，**`balance` 是记账事务同步的冗余列**（可与流水对账），接口不接收手改；班级名跨班唯一（重名 400）。
- 参数校验：Pydantic v2 模型（`Field` 约束：非空、`ge=0.01`、小数位 ≤2、分页 `ge=1`），camelCase 字段名与前端约定一致。
- **审计留痕字段（第十九轮）**：三个 VO 各加一组「谁在什么时候动过」的键，**对所有角色稳定存在**，未发生动作时为 `null`（不是缺键、也不是只在某角色下出现）：

  | VO | 新增键 | 何时被写入 |
  |----|--------|------------|
  | `record_vo` | `voidedBy` / `voidedByName` / `voidedAt` | `POST /records/{id}/void` |
  | `batch_vo` | `closedBy` / `closedByName` / `closedAt` | `POST /batches/{id}/close` |
  | `notice_vo` | `updatedBy` / `updatedByName` / `updatedAt` | `PUT /notices/{id}`（编辑/置顶/下架/恢复**都算**） |

  `notice_vo` 的 `createdBy`（谁发的）**不被** `updatedBy` 覆盖，两条线独立。姓名的批量补齐并进各 service **已有的那一次** `SELECT sys_user WHERE id IN (...)`（把审计 id 并进集合），不引入 N+1。`DELETE` 类端点是硬删，**不产生**留痕，详见 §4 末尾与 §8 第十九轮。
- 全局异常：body 字段校验错 → 400「参数校验失败」+ 字段错误列表 `[{field,message}]`；请求体格式错 → 400「请求体格式不正确」；query/path 类型错 → 400「请求参数不合法」；业务异常 `BizException(code,msg)`；未知路径 404「接口不存在」；兜底 500「系统繁忙，请稍后重试」。
- 事务：记账/作废/删除/标记缴费一律在 `session.begin()` 事务内完成，对 `cls_class.balance` 用
  `UPDATE cls_class SET balance = balance + :delta WHERE id=:id` 原子更新。

**已知限制（M3 收尾时明确，M4 再评估）**
1. **收入登记页不关联批次/成员**：`POST /records` 不接受 `batchId/userId`。成员缴费的唯一写入路径是批次「标记缴费」（同事务写流水 + 缴费状态 + 余额），保持单一资金写入路径、避免两套逻辑漂移；如需「散收抵扣」，再评估在 `RecordRequest` 扩展并复用 `batch_service.pay` 的事务内核。
2. **`fee_payment.status` 的 `REFUNDED` 枚举暂无写入路径**：退款场景当前做法是「作废原流水 → 缴费状态回退 UNPAID」（红冲即退款），已覆盖演示需求；`REFUNDED` 保留在枚举中供后续使用。
3. ~~`GET /records/export` 等完整版接口~~：**已于第十三轮交付**（xlsx，见 §5 接口表）。本节无遗留待办接口。
4. **导出无行数上限**：`/records/export` 一次性在内存生成 xlsx（班级量级足够）；若未来单班流水达十万级，需改流式写出或加行数上限，避免内存尖峰。

## 7. 安全与质量

| 项 | 方案 |
|----|------|
| 密码 | BCrypt（强度 10），接口不回传密码字段 |
| 会话 | JWT HS256，有效期 2h；`Authorization: Bearer`；401 统一跳登录 |
| 越权 | 后端 `_STAFF_ROUTES` 角色路由表（中间件）+ 端点级 `require_role` 双重拦截；所有按 id 的操作校验 `class_id` 归属 |
| SQL 注入 | SQLAlchemy ORM/参数绑定，禁止字符串拼接 |
| 金额 | `DECIMAL`；Pydantic `Decimal` 入参校验；`Decimal.quantize(0.01, HALF_UP)` |
| 上传 | 小票票据：≤5MB，**按内容魔数嗅探**（不信任扩展名/Content-Type，拒绝伪装扩展名的非图片），uuid 随机文件名落 `uploads/receipts/`（目录由 `CLASSFEE_UPLOAD_DIR` 可配）；读取时 `resolve()` 校验不越出上传根目录（防路径穿越），查看需登录 + 本班流水引用，删除流水时回收文件 |
| 并发 | 记账串行化到事务内原子 `UPDATE balance`；批次缴费靠 `uk_batch_user` 唯一键防重复 |
| 日志 | 记账/作废/改密打 `INFO` 审计日志（完整版落库 `sys_audit_log`） |

**用户验收修复交付记录（第十七轮 · 归属权 A 方案）**

**问题**：三张业务表都记了 `created_by`，但改/删路径一直只校验「是不是同一个班」，于是出现**「删不掉班主任的账号，却能删掉班主任记的账」**——第十五轮加的等级只管住了账号管理，账目这条路是敞开的。实测：班长/生活委员可以作废、删除班主任记的流水（并自动回滚余额、不可恢复），可以改班主任发的公告，可以删/关班主任建的收费批次。

**选定方案 A（谁创建谁负责）**，在 B（等级+归属双闸）之前落地，因为用户要的是责任可追溯。

| 位置 | 改动 |
|------|------|
| `security.require_ownership()` | 新增护栏：`actor_id != created_by` 即 403，报错带创建人 id，引导找创建人协作 |
| 流水 | `void_record` / `delete_record` 加闸（删除会回滚余额，闸门放在最前面） |
| 公告 | `update_notice`（含置顶/下架/恢复）/ `delete_notice` 加闸 |
| 批次 | `close` / `delete_batch` 加闸（关闭后不能再收款，是实质动作） |
| `batch_vo` | 补 `createdBy` + `createdByName`（原来没有，前端无法做按钮收敛） |
| 前端三处 | `isMine()` 收敛：账本隐藏他人流水的作废/删除并显示「X 记的」；公告隐藏置顶/下架/编辑/彻底删除并显示「X 发布的」；批次隐藏关闭/删除 |

**刻意不设闸的一处**：`pay`（标记已交）。收款是**协作动作**，闸门加在缴费上会把账卡死——班主任必须能给班长建的批次登记缴费。回归里专门锁了这条（`班主任给班长建的批次标记缴费 -> 200`）。

**A 方案的已知代价（用户已知情选择）**：班主任也动不了班长的数据。实测确认——班主任删除班长的流水 403、关闭班长的批次 403。这是为了责任可追溯而接受的取舍；协作靠「报错带创建人 + 界面显示创建人」来支撑。

**验收**：后端归属权专项 24/24；回归 **236/236**（新增 19 条：越级 403×6、被拒后数据未被改动×2、A 方案代价×2、VO 字段×2、缴费不设闸×1 等）；`vue-tsc` 0、`build` 0；浏览器实测三处按钮收敛正确（班长看老师的数据：账本无作废/删除、公告无置顶下架编辑、批次无关闭删除）。

> **本轮还修掉回归脚本自身的一个缺陷**：`test_a06` 里原来的「改/删他班类别」断言是**无效且危险**的——`GET /api/categories` 按 `class_id` 过滤，只可能返回本班类别，所以「他班类别」根本拿不到；原实现用 `classId not in (None, cls0.get("id"))` 去列表里找，一旦 `GET /api/class` 那一瞬没返回（`cls0` 为空 dict），条件就退化成「取列表第一个」——**实测真的把种子类别 `捐款` 停用过一次，且是间歇性的**（取决于那一次 `/api/class` 是否恰好就绪，极难排查）。已删除该断言（跨班隔离改在「用他班 categoryId 登记本班流水」这条真正可构造的场景上验证），并加两道护栏：① 所有破坏性操作前用 `guard_probe()` 重新确认目标是本脚本造的探针（名字以 `regress` 开头），否则拒发；② 开局拍**类别字典指纹**、收尾逐项比对，任何一条被改名/停用/改排序都会指名道姓报出来。连跑 3 次验证：217/217，种子字典每次完好，服务端访问日志确认只碰探针 id。

> **本轮又抓到两个自己的 bug**（都是我写完自己测出来的，记下来当教训）：
> ① **VO 契约时有时无**。最初 `my*` 只给非运营角色，班长访问时拿到的是 `undefined` 而不是 `null`，前端 `=== null` 判断落空，一路掉到最后把「你不属于缴费对象」显示成「**未缴费**」——一个运营角色被告知欠着班费。修法不是让前端写 `== null` 兜底，而是**让契约对所有角色稳定存在**（运营角色值为 `null`），前端再加 `== null` 双重保险。
> ② **又犯了 markdown 外泄**。修完 `profile` 页的 `**你自己**` 之后，我在新建的 `my-fees` 页又写了一遍 `**你自己**`，浏览器实测 `literalAsterisk: true` 当场抓住。凡是用户能看到的文案，`**` 必须写成 `<strong>`。

**遗留（非缺陷）**

**用户验收修复交付记录（第十九轮 · 审计留痕）**

**问题**：第十七轮定了归属权 A 方案（谁创建谁负责），初衷是**责任可追溯**；但改/删路径只校验了「是不是同一个人」，**没留下任何痕迹**。流水被作废后只显示一个「已作废」标签，看不出是谁干的、什么时候干的；批次被关闭、公告被下架同理。A 方案挡住了越权，却答不了「这笔账为什么消失」。

| 表 | 列 | 回答什么问题 | 写入点 |
|----|----|--------------|--------|
| `fee_record` | `voided_by` / `voided_at` | 这笔账是谁作废的、什么时候 | `record_service.void_record`（与 `status='VOID'` 同一条 UPDATE） |
| `fee_batch` | `closed_by` / `closed_at` | 这个批次是谁关的、什么时候 | `batch_service.close` |
| `sys_notice` | `updated_by` / `updated_at` | 这条公告最后是谁改的、什么时候 | `notice_service.update_notice`（编辑/置顶/下架/恢复**都走这一条**） |

**关键设计取舍：删除仍然无痕，这是有意的。**

`delete_record` / `delete_batch` 是**硬删**——行都没了，物理上留不下任何记录。留痕路径是「**作废 / 下架**」，不是删除。因此：

- 界面文案一律引导「**记错优先作废**（红冲留痕，可查是谁作废的）」，而不是「删除更彻底」
- 公告的 `updated_by` 恰好覆盖了删除前的最后一跳：删之前必须先下架（`status=0`），而**下架本身就是一次 `update`**，所以「谁下的架」被记下来了；只是「谁删的行」仍然查不到

**公告的两条独立的线**：`created_by`（谁发的）不被编辑覆盖，`updated_by`（谁最后动的）单独记。改过 5 次的公告，能同时回答「谁发的」和「最后谁动的」。

**迁移**：`seed.add_audit_columns()` 逐列查 `INFORMATION_SCHEMA`，缺了才 `ALTER` —— 幂等，新库由 `schema.sql` 建好（DDL 已同步），既有库靠迁移补。**实测第二次运行输出「审计列已齐全，跳过迁移」**。

**VO 与姓名批量补齐**：`record_vo` / `batch_vo` / `notice_vo` 各自加 `*By` / `*ByName` / `*At` 三个键；姓名一律并进**已有的那一次** `SELECT sys_user WHERE id IN (...)`（把 `voided_by` / `closed_by` / `updated_by` 的 id 并进集合），**不引入 N+1**。三个键对所有角色稳定存在，未发生动作时为 `null`（沿用第十八轮的「契约稳定」教训）。

**界面**（窄桌面卡片视图与宽桌面表格视图两处都改了）：

| 位置 | 显示 |
|------|------|
| 账本 | 状态列「已作废」标签旁挂一个虚线小角标「谁作废」，hover 显示 `由 X 于 时间 作废`。状态列宽 80→**150** 并加 `white-space: nowrap`（实测 80px 下角标换行被行高裁掉，132px 仍压列边界，150px 实测右侧余 39px 不溢出） |
| 批次 | 卡片脚注从「已关闭 · 0/1 人已缴」变为「已关闭 · **由 X 关闭** · 0/1 人已缴」 |
| 公告 | 元信息行追加「· 最后由 X 编辑于 时间」。条件只看**有没有编辑过**，不看是否同一人 —— 同一人改的，「内容比发布时间新」这条信息读者也需要 |

**隐私边界**：作废人 / 关闭人 / 编辑人姓名与**已有的 `createdByName` 同级**（发布人姓名本来就对全班可见），不引入新的个人信息暴露。MEMBER 侧实测：状态列有留痕、操作列无任何按钮、无「收费批次」入口、公告有编辑留痕。

**验收**：审计专项 19/19；回归 **258/258**（新增 19 条：三个动作的「谁/何时」各 3 条、未发生动作时字段为 null、新建时为 null、VO 键齐全、`createdBy` 不被编辑覆盖、接口未被打断）；`vue-tsc` 0；浏览器实测三个角色看三处留痕正确。

> **本轮的教训**：
> ① **「A 方案 = 责任可追溯」这句话当时只兑现了一半**。归属权闸门只解决了「谁能动」，没解决「谁动过」。设计一个可追溯机制时，要问的是**两个**问题：谁**能**做、谁**做过**。只答第一个就宣布完成，是把「授权」当成了「审计」。
> ② **审计列的边界要主动说清，而不是等被问**。硬删留不下痕迹是物理事实，不是疏漏；但如果我不写进文档，半年后有人会问「为什么删了就没了」而我只能现场解释。写进设计文档的这一段比代码本身更重要。
> ③ 界面改动**必须量像素**。状态列 80px 改 132px 时我是目测的，浏览器截图里角标明显还在压边界；改成读 `getBoundingClientRect()` 比较 `badgeRight` 与 `colRight` 才定下 150px。目测在这个尺寸级别上会连续错两次。

**用户验收修复交付记录（第二十轮 · 缴费对象口径）**

**问题**：用户反馈「班主任没有缴费」，要求把「我的缴费」从班主任的界面里删掉。查证时发现它**不是一个孤立的界面问题，而是一个业务口径错误**：

第十四轮定的口径是「缴费对象 = 只有 `MEMBER`」，理由写的是「运营角色是管账的人，不该出现在缴费名单里，否则建批次会把自己也算成未缴费，完成率永远差几个人」。**这个理由只对班主任成立**——班主任是 `.env` 声明的老师账号、不是学生，班费跟他无关。但生活委员和班长是在自己班里承担班务的**学生**，班费照交。

沿用旧口径的真实后果不是「完成率不好看」，而是**班里收不到他们的班费**：他们不在缴费名单里 → 成员缴费页列不出他们 → 代为登记无处可登记。实测确认：班长的「我的缴费」页显示的是「不在缴费名单 / 你的角色是运营角色，不属于缴费对象」加一个转去「成员缴费」的按钮，一个纯死胡同。

| 位置 | 改动 |
|------|------|
| `batch_service.PAYABLE_ROLES` | **新增常量** `("MEMBER", "ADMIN", "MONITOR")`，作为缴费对象的**唯一事实来源** |
| `batch_service._class_members` | `role == "MEMBER"` → `role.in_(PAYABLE_ROLES)`（建批次时生成缴费行） |
| `batch_service.members()` | 同样的 `== "MEMBER"` → `in_(PAYABLE_ROLES)`（成员缴费页列名单） |
| `seed.backfill_payable_roster()` | **新增幂等迁移**：给**已存在的 OPEN 批次**补上生活委员/班长的缴费行 |
| `router/index.ts` | `/my-fees` 的 `meta.roles` 改为 `['ADMIN','MONITOR','MEMBER']`——**排除班主任** |
| `layout/SideNav.vue` | 侧栏「我的缴费」加 `roles: PAYABLE`，新增 `PAYABLE = ['ADMIN','MONITOR','MEMBER']` |
| `views/my-fees/index.vue` | 死胡同文案里去掉「班主任」（他已进不来这页） |

**两处口径必须一起改**，这是本轮最容易出错的地方：只改 `_class_members` 会出现「批次里已经生成了缴费行、成员缴费页却列不出这个人」——点「标记缴费」报 400「该成员缴费状态不存在」，而他自己在「我的缴费」里还看不到欠费。所以特意把口径收敛成一个常量，两处都从它取。

**迁移只补 OPEN 批次**，这是刻意的：已关闭批次是历史记录，补一堆 `UNPAID` 行会把当时的完成率改写成另一个数（等于篡改历史账），而且关闭后本来就拒绝收款，补了也无法销账。

**班主任的处理是纯界面层的**：`GET /api/batches` 对他照常返回完整 VO（他要给班里管收费批次，需要看批次），`roles` 挡的只是「找不到入口 + 手输 URL 进不去」这一层。**权限边界仍然在后端**。

**验收**：专项 19/19；回归 **276/276**（新增 18 条：名单含三类学生 / 不含班主任 / 成员缴费页与批次名单角色集合一致 / 班长与生活委员 `myStatus = UNPAID` / 班主任 `myStatus = null` / 班主任代登记 200 / 迁移幂等无重复行 / 清理后余额归零无残留流水）；`vue-tsc` 0；浏览器四角色实测——班主任侧栏无入口且手输 URL 被弹回仪表盘；普通成员看到「已缴费 · 实收 300.00」；班长看到「**未缴费 · 还剩 6 天**」（本轮之前是「不在缴费名单」）。

> **本轮踩到的两个坑**：
> ① **口径写死两处 = 迟早漂移**。`role == "MEMBER"` 这个判断在 `_class_members` 和 `members()` 里各写了一遍，任何一次只改一处都会造出「一边列一边不列」的死角，而且是那种**本地测试看不出来、上线才发现**的（测试里如果名单恰好只有普通成员，两处不一致也测不出来）。改口径时先问「这个定义在几个地方被复述过」，答案是 >1 就抽常量。
> ② **我自己写的探针清理差点造成账实不符**。清理脚本里我图省事用了裸 SQL `DELETE FROM fee_batch/fee_payment`，**绕过了 `delete_batch` 的级联删除与余额回滚** —— 结果自动生成的收入流水留在表里、余额停在 600.00、批次却已经没了。发现后改回「凡会动钱的清理一律走 API」，并在探针里加了两条断言（清理后余额归零 / 无残留流水）把这个坑变成会失败的检查。教训：**验证脚本和被验证系统走不同的通道时，等于在测一条不存在的路径**。

**用户验收修复交付记录（第二十二轮 · 编码规则定型 + 闸门自动化）**

**用户指令**：「以后写 Nginx、Shell、Dockerfile、各类程序配置文件，**一律使用 UTF-8 无 BOM**，不要用 Windows 记事本编辑。」

把这条从"提醒"变成**可执行的规则**，做了三件事：

**① 确立判据**：分界线不是文件类型，而是**谁来读这个文件**。

| 读者 | 编码 | 范围 |
|------|------|------|
| **程序**（nginx / MySQL / shell / Docker / 任何按字节或按行解析的解析器） | **UTF-8 无 BOM** | `*.conf`、`*.sh`、`*.bash`、`Dockerfile*`、compose yml、`*.sql`、`*.json`、`*.toml`/`*.ini`/`*.cfg`、`*.bat`、`*.ps1`、`.env*`、CI 配置 |
| **人**（编辑器 / GBK 工具 / Notepad） | **UTF-8 带 BOM** | `docs/*.md`、`README.md`、`*.txt` |
| 人机都不敏感 | 无所谓 | 全部 `.py`（Python 自动识别源文件 BOM） |

**中文注释在「无 BOM」那一侧完全安全**——这条要写清楚，否则容易误以为"要写英文注释"。`nginx.docker.conf` 与 `schema.sql` 里的中文注释从来没出过问题，**坏的只有 BOM 本身**。

**② 闸门从"点名"升级为"自动发现"**（`test_a00_encoding_guards`，回归第一个用例）：

| 检查 | 作用 |
|------|------|
| 6 条「点名文件必须无 BOM」 | 守住已知的坑 |
| 2 条「markdown 必须保留 BOM」 | 反向断言，防止将来被「统一风格」误删 |
| **1 条「自动扫描全仓库」** | 扫 `_PROGRAM_READ_SUFFIXES`（18 种扩展名 + `Dockerfile`/`Makefile`/`.env` 等）里的所有文件，**任何带 BOM 的都报出来** |

**自动扫描才是长期防线**：前两种只管登记过的清单，而清单会漏——新建一个 `deploy.sh` 的人不会想到去改 `must_be_clean` 列表。实测验证：临时造一个带 BOM 的 `server-py/deploy.sh`，闸门立刻报 `284 passed, 1 failed` 并指名该文件；恢复后 285/285。

**③ 顺带发现并修掉两个漏网**：`server-py/Dockerfile` 与 `web/Dockerfile` **也都带 BOM**（此前谁也没检查过，因为它们不在任何清单里——正是自动扫描的典型收获）。已去 BOM。注意 `server/Dockerfile`（Java 版，不参与部署）本来就是干净的。

**验收**：回归 **285/285**；并两次实测闸门会失败（点名项 + 自动扫描项各一次）。

> **本轮的方法论收获**：
> ① **规则要挂在能自动失败的地方**。「以后一律用无 BOM」这种指令如果不落到检查上，下一个人（或下一个我）迟早会忘。写成回归里的一个用例 + 覆盖全仓库的自动扫描，比写在文档里可靠得多。
> ② **「列出已知坏文件」和「判定一类文件」是两种不同的覆盖**。前者的边界永远等于已知坏文件的数量；后者才会在新文件出现时自动生效。**能用后者就别用前者**——本轮正是靠自动扫描发现了两个从没进过清单的 Dockerfile。
> ③ 用户给的指令要**补上判据而不是照抄**。原文说"配置类文件用无 BOM"，但没说清「`.md` 反而要有 BOM」「中文注释完全安全」这两点——照抄会让后来者要么把 md 的 BOM 也删了、要么以为写配置必须避开中文。**分界线给成「谁读这个文件」，两边都判得动。**
`role == "MEMBER"` 这个判断在 `_class_members` 和 `members()` 里各写了一遍，任何一次只改一处都会造出「一边列一边不列」的死角，而且是那种**本地测试看不出来、上线才发现**的（测试里如果名单恰好只有普通成员，两处不一致也测不出来）。改口径时先问「这个定义在几个地方被复述过」，答案是 >1 就抽常量。
> ② **我自己写的探针清理差点造成账实不符**。清理脚本里我图省事用了裸 SQL `DELETE FROM fee_batch/fee_payment`，**绕过了 `delete_batch` 的级联删除与余额回滚** —— 结果自动生成的收入流水留在表里、余额停在 600.00、批次却已经没了。发现后改回「凡会动钱的清理一律走 API」，并在探针里加了两条断言（清理后余额归零 / 无残留流水）把这个坑变成会失败的检查。教训：**验证脚本和被验证系统走不同的通道时，等于在测一条不存在的路径**。

**用户验收修复交付记录（第二十一轮 · nginx 配置 BOM）**

**问题**：用户在服务器上 `docker compose up` 失败，frontend 容器起不来：

```
[emerg] unknown directive " server" in /etc/nginx/conf.d/default.conf:1
```

**根因**：`web/nginx.docker.conf` 开头是 **UTF-8 BOM**（`EF BB BF`），后面才是 `server {`。nginx 按字节读配置，把 BOM 和 `server` 解析成**一个 token**，于是 `server` 这个指令「不存在」——报错里那个引号内的空格就是 BOM 被终端渲染的样子。`web/Dockerfile:14` 的 `COPY nginx.docker.conf /etc/nginx/conf.d/default.conf` 原样复制，BOM 一起进了容器。

**这是第 19 轮 `schema.sql` 那个 BOM 陷阱的第二次发作**，但表现完全不同，必须一起记住：

| 文件 | 被谁按字节解析 | 加了 BOM 的后果 | 隐蔽性 |
|------|--------------|--------------|--------|
| `server-py/db/schema.sql` | `run_schema()` 按行切 SQL | 首行 `-- 1) 班级表` 不被当注释剔掉 → 第一条建表语句语法错 → 被 `except ProgrammingError: continue` **静默吞掉** | **静默**：新库少 `cls_class` 一张表，启动日志一个字不报 |
| `web/nginx.docker.conf` | nginx | `unknown directive " server"` | **响亮**：容器直接起不来 |

同一个根因，一个静默一个炸响。**共同点是：都只有真正跑起来才暴露，而本机没有 Docker。**

**修复**：

| 文件 | 处理 |
|------|------|
| `web/nginx.docker.conf` | **去 BOM**（必须，否则 frontend 起不来） |
| `docker-compose.yml` / `docker-compose.use-existing-db.yml` / `.env.example` | 一并去 BOM。compose 的 YAML 解析器目前容忍 BOM（用户那次 `up` 能跑到 nginx 阶段就是证据），但 **systemd 的 `EnvironmentFile` 不剥 BOM** —— 留着是定时炸弹 |
| `.md` / `.py` | **保留原样**：`.md` 的 BOM 正是为 GBK 工具准备的；`.py` 由 Python 自动识别源文件 BOM |

**回归加了文件编码闸门** `test_a00_encoding_guards`，作为**第一个**用例（8 条断言：6 个「必须无 BOM」+ 2 个「markdown 必须保留 BOM」）：

| 类别 | 文件 | 理由 |
|------|------|------|
| 必须**无** BOM（**程序**读） | `web/nginx.docker.conf`、`server-py/db/schema.sql`、`web/package.json`、两个 compose、`.env.example` | nginx / MySQL / 工具按字节解析，BOM 是内容的一部分 |
| 必须**有** BOM（**人**读） | `docs/*.md` | 中文 Windows 的 GBK 工具要读，无 BOM 是乱码 |
| 无所谓 | 全部 `.py` | Python 自动识别源文件 BOM |

**为什么放进回归而不是写个独立脚本**：本项目的回归是唯一「每次交付都跑」的自动化闸门。独立的检查脚本需要人记得执行，而这类 bug 的特点恰恰是**没人会想到去跑那个脚本**。反向断言（markdown 必须保留 BOM）也是刻意的——防止将来有人以「统一风格」为名把 markdown 的 BOM 一起删掉，那会换一种方式复现同样的乱码问题。

> **本轮的教训**：

**本项目反复踩到的五个坑**（细节见 §8 对应轮次）：

1. **既有库不会自动改结构**——DDL 是 `CREATE TABLE IF NOT EXISTS`，改文本对已建库无效；给 ENUM 加值会直接 500（`DataError 1265`）。任何列定义变更都要配幂等 `ALTER` 迁移。
2. **「含中文的文件一律加 BOM」是条会伤人的通则**（第十九、二十一轮各中一次）。它是为「人用 GBK 工具打开」设计的，但对**被程序按字节解析**的文件，BOM 不是无害的解码提示，而是**内容的一部分**：

   | 文件 | 被谁解析 | 加 BOM 的后果 | 隐蔽性 |
   |------|---------|-------------|--------|
   | `server-py/db/schema.sql` | `run_schema()` 按行切 SQL | 首行注释不被剔掉 → 第一条建表语句语法错 → 被 `except ProgrammingError: continue` **静默吞掉** → **新库少 `cls_class`** | **静默**，启动日志零告警 |
   | `web/nginx.docker.conf` | nginx | `unknown directive " server"`（BOM 与 `server` 读成一个 token） | **响亮**，容器起不来 |

   `schema.sql` 那条链路是三步叠加：`read_text(encoding="utf-8")` 不剥 BOM（要 `utf-8-sig`）→ 注释过滤 `ln.lstrip().startswith("--")` 而 `"\ufeff".isspace()` 是 `False` → 切出的首条语句 MySQL 不认作注释。**危险在于它与「出错继续」的容错设计叠在一起**——容错本身是对的，错在丢掉了错误信号。

   **分界线是「谁来读这个文件」**，不是文件类型：

   | 读者 | 编码 | 本项目的文件 |
   |------|------|------------|
   | **程序**（nginx / MySQL / shell / Docker / 任何按字节或按行解析的解析器） | **UTF-8 无 BOM** | `*.conf`、`*.sh`、`Dockerfile*`、compose yml、`*.sql`、`*.json`、`*.bat`、`.env*`、CI 配置、各类程序配置 |
   | **人**（编辑器 / GBK 工具 / Notepad） | **UTF-8 带 BOM** | `docs/*.md`、`README.md`、`*.txt` 等给人读的文档 |
   | 人机都不敏感 | 无所谓 | `.py`（Python 自动识别源文件 BOM，两种都能跑） |

   **中文注释在「无 BOM」那一侧完全安全**——`nginx.docker.conf`、`schema.sql` 里的中文注释从来没出过问题，坏的只有 BOM 本身。写这类文件时放心写中文，只是不带 BOM。

   **编辑方式**：用 `edit` / `write` 工具或任意编辑器保存为 **UTF-8 无 BOM**；**不要用 Windows 记事本**（它默认写 GBK，且在部分版本里对已有文件会追加 BOM）。VS Code 右下角能直接看到当前是 `UTF-8` 还是 `UTF-8 with BOM`，保存前扫一眼。

   **落地方式**：清单由回归的 `A0. 文件编码闸门` 强制（6 条「必须无 BOM」+ 2 条「md 必须保留 BOM」）。新增配置文件时，把它的路径加进 `test_a00_encoding_guards` 的 `must_be_clean` 列表——闸门只管你登记过的文件，**新文件不登记 = 不受检查**。
3. **角色白名单散落三处**——前端 `isStaff`、侧栏 `STAFF`、路由 `meta.roles`，漏任一处会出现「有权限却看不到入口」或反之。
4. **PowerShell 5.1 编码坑（历史教训，回归脚本已于第十六轮迁走）**——`.ps1` 存 UTF-8 **无 BOM** 时按 ANSI（中文 Windows 即 GBK）解析，文件里的中文注释会变乱码，**乱码吞掉换行/引号会让紧跟其后的 `OK` 断言静默失效**（表现为 `st=` 空值、`RESULT` 少 2 项）。当时的两条硬规矩：**必须带 UTF-8 BOM**（实测同一份脚本无 BOM 149/151、带 BOM 151/151）；**断言里的字符串字面量保持 ASCII-only**，中文只允许出现在注释。另：`ConvertFrom-Json` 遇乱码直接抛错，不要用 `curl.exe` 输出直接喂它。
   - **现状**：回归脚本已改写为 `server-py/tests/api_regression.py`（Python 3 源码无 BOM 问题，字面量也不必 ASCII-only）。上面的坑只在**你临时写 `.ps1` 排查问题时**才会遇到。
